3. **先做三件（约 12–15 人日）**：~~① 输出规格面板 ② 版式基础参数 ③ 渲染性能与健壮性~~ → **✅ 2026-11-04 已交付**（见 5.3）。N4/N5/X8 已在 Sprint A 交付（见 5.4），X1/X2 已在 Sprint B 交付（见 5.5）；下一步按 5.2 顺序：X9 守输入质量 → X5/X6/X7。

### 1.2 四个被低估的约束（直接影响路线图）

**① 长图会被降采样，且比想象中更早发生（改版后已提示，但仍不可控）。**
输出上限同时约束最长边 8192px 与 2000 万像素（`stitchRenderer.js:3-6`）。对手机截图（1179×2556）实测（用仓库函数计算）：

| 场景 | 原始画布 | 实际输出 | 缩放 | 后果 |
|---|---|---|---|---|
| 3 张 iPhone 截图 | 1179×7668 | 1179×7668 | 1.000 | 可用 |
| 4 张 iPhone 截图 | 1179×10224 | 944×8191 | 0.801 | 文字缩小约 20% |
| 6 张 iPhone 截图 | 1179×15336 | 629×8191 | 0.534 | 宽度只剩 53%，正文文字基本不可读 |
| 6 张 Android 截图 | 1080×14400 | 614×8191 | 0.569 | 同上 |
| 6 张横向拼接 | 7074×2556 | 7074×2556 | 1.000 | 不受影响 |

结论：**纵向超过 3 张手机截图就开始掉清晰度**，而这个产品名字就叫"长图拼接"。这是当前最该优先解决的产品问题之一，且与 README 中"必要时等比缩小"的承诺并不矛盾——缺的是"告知 + 可选长图模式"。

补充计算：若只把最长边上限放宽到 16384、仍守 2000 万像素，则 6 张 iPhone 截图可保持 `1179×15336`（18.1MP，缩放 1.000）；4 张为 `1179×10224`（12.1MP）。也就是说，**单靠"长图模式"就能把核心场景从"文字不可读"救回"原分辨率"**，代价是需要真机验证 18MP 画布的 Safari/移动端内存。

**② 低分辨率图会被放大。✅ 已修复。**
布局不再对图片做任何放大：小图保持原始尺寸、居中留白，缩略图下方显示原图 `宽×高`，并在混入小图时提示「保持原始尺寸居中（不放大）」。

**③ 本地处理的代价是"刷新即全丢"。**
没有 IndexedDB（`App.jsx` 只持久化 theme），也没有任何恢复机制。用户误刷新/崩溃 = 重新选图、重新排序、重新调参。竞品是云端会话，我们越强调"本地不上传"，越需要本地会话恢复来兑现同等安全感。

**④ 调参等于全量重算。✅ 已修复（解码层）。**
位图按 `id|url` 缓存，预算变化时复用/缩放；设置变更 160ms 防抖；实测 6×12MP 场景缓存命中后解码 0ms（首次 521ms），删一张图不再重解码存活图。PNG 编码仍在主线程、约 300ms；下一步是「预览画布 + 按需/Worker 编码」。

### 1.3 已具备、值得放大的资产

- **零上传的架构事实**：全站无 fetch/XHR 上传逻辑，图片只存在于 Object URL 与 Canvas 中，导出时 Canvas 重编码还会丢掉 EXIF/GPS。
- **波浪缝的视觉签名**：不是通用拼图工具会做的细节，可低风险扩展为"缝隙样式"，成为识别度来源。
- **克制的 6 张上限**：交互、布局、认知负担都可控；这是"30 秒完成"的基础，暂不应为了对标竞品而放弃。
- **正确的内存纪律**：Object URL 释放、位图 `close()`、分层像素预算（`stitchRenderer.js:36-138`）都已实现，属于很多同类工具没有的工程底子。

### 2.2 从这些页面能读到的共性诉求

1. **"拼多少张"是显性焦虑**：20（PhotoJoiner FAQ）、30（IMGonline 拼图上限）、300（Picsew）都被写进卖点。我们的答案是反过来的——**6 张以内做到最顺**，但必须把"6 张的质量"做到无可挑剔。
2. **不同尺寸混排是核心难题**：PhotoJoiner 专门强调 "Merge Images Without Cropping"、IMGonline 给适配模式 + 裁切锚点、PineTools 给 5 种尺寸处理。我们目前只有一个"按最大宽度缩放 + 居中留白"，还附带小图放大问题。
3. **间距/边框/圆角/背景是拼图工具的"空气"**：改图鸭、稿定、PhotoJoiner、PineTools、IMGonline 全部提供。我们恰好相反：**有背景色渲染能力，却没有 UI 入口**。
4. **输出必须可控**：IMGonline 提供 JPEG 质量 1–100 与 PNG-24，Picsew 提供 PDF 与"切成多张整齐切片"。我们只有 PNG；改版后尺寸/体积已可见，但格式与质量仍不可选。
5. **长截图是独立且更高频的场景**：Picsew 的整页描述都围绕"聊天记录、长文章、票据、网页、评论区"，并强调重叠识别与手动微调。这正是网页端"传 6 张截图拼长图"的真实用户任务。
6. **隐私正在变成卖点**：IMGonline 在站点说明里写"所有处理后的图片最多在服务器保留 2 小时"（原文："*All processed images are stored on this website no more than 2 hours.*"），Picsew 把"模糊/马赛克隐藏姓名、头像、账号、地址"放进核心卖点。前者是我们的对比面，后者是我们该补的本地能力。

### 2.3 我们的空位

> 用户不是要"另一个拼图编辑器"，而是**"把手上这几张截图/照片，在 30 秒内变成一张能直接发出去、且不担心隐私的长图"**。

因此路线图的重心不是加数量、加模板，而是：
- **补闭环**：输出规格（格式/质量/尺寸/长图）→ 成品可用；
- **补必备参数**：间距/边距/背景/裁剪对位 → 成品好看、不变形；
- **押差异**：重叠感知合并、智能缝隙、自动去状态栏 → 竞品在网页端没做好的长截图体验。

## 3. 北极星与必须保护的强项

### 3.1 北极星

> **在浏览器里 30 秒内，把 2–6 张图片拼成一张可直接发布的长图；图片从不离开设备。**

判断一个需求该不该进路线图，只问三件事：
1. 是否让"从选图到导出"更短，或成品更可直接使用？
2. 是否仍然可以在**无网络、无账号、无上传**下完成？
3. 是否强化"长图/截图拼接"这个心智，而不是把产品拉成通用设计工具？

### 3.2 四个要保护的强项

| 强项 | 为什么值钱 | 如何保护 |
|---|---|---|
| **本地零上传** | 聊天记录、证件、票据、工作截图都不适合上传；竞品服务器保留 2 小时是不可接受的风险面 | 任何新能力不得引入上传；不引入第三方分析脚本；在 UI 提供"本地处理"可验证入口（见 9.2） |
| **快** | 无上传队列、无登录、无模板加载，点开即用 | 用性能预算守门（第 9 节）；新增能力不得拖慢首屏与调参响应 |
| **6 张的简单性** | 降低选择成本，保证 30 秒可完成 | 数量上限不主动提高（L4 仅在性能与体验双达标后作为实验）；不引入"无限画布" |
| **波浪缝识别度** | 同级工具里少见的细节，形成视觉记忆 | 作为"缝隙样式"的核心保留，参数化但不花哨；不为了功能数量删掉它 |

### 3.3 不可逾越的红线

- 图片、缩略图、文件名、EXIF 一律不出设备（含"匿名"上报）。
- 不做需要上传才能用的能力（AI 修图/抠图/超分等）。
- 不引入账号体系——没有账号就没有"云端副本"的期待与合规负担。
- 不因为新增参数而让默认流程变长：默认设置应当一键可导出。

## 8. 三个 moonshot（唯一适合"拼接"的押注）

> 判定标准：只在**网页端、纯本地、现有 Canvas 管线**可落地时才立项；每个 moonshot 先做 3–5 天 spike，达不到成功标准就放弃，不影响主线。

### 8.1 M1 · 重叠感知长截图合并

**用户任务**：用户在手机上连续截图（聊天记录、网页、订单、文章），上传 3–6 张有重叠区域的截图，期望得到一张"无缝、没有重复状态栏"的长图。这是 Picsew 的核心场景；在我们抓取的网页端工具里没有看到重叠识别能力。

**为什么是我们**：我们已经有 6 张上限、Canvas 管线、像素预算与本地承诺；缺的只是"相邻图重叠检测"这一步预处理。做成了，产品从"拼图工具"升级为"长截图工具"。

**与现有管线结合点**
- 在 `createStitchPlan` 之前插入 `computeCropPlan(bitmaps)`：为每张图算出 `topCrop` / `bottomCrop`（去掉重复状态栏、导航栏、重叠区）。
- `stitchLayout` 的 placement 增加 `sourceRect`；`stitchRenderer` 改用 9 参数 `drawImage`（天然支持源矩形）。
- 输出高度 = Σ(各图裁剪后高度)，再走 N1 的长图模式与输出上限。
- 需要把 `imageIntake` 的宽高比限制（30:1）与"同宽截图"分组提示结合，避免把不相关图片误合并。

**算法（可在 Worker 内实现）**
1. 每张图下采样到宽 256 的灰度图（`createImageBitmap`/OffscreenCanvas）。
2. 对相邻两张图，在候选重叠比例区间（如 5%–90% 高度）滑动，计算行签名（行均值 + 行梯度能量）的归一化差异；取 top-3 候选。
3. 在 top-3 上回到较高分辨率做 ±4px 细化，输出置信度。
4. 置信度高于阈值才自动裁剪；否则进入"手动微调拼接点"模式（Picsew 也提供手动微调，说明自动并非 100% 可靠——[来源](https://apps.apple.com/cn/app/picsew-%E6%BB%9A%E5%8A%A8%E6%88%AA%E5%9B%BE-%E9%95%BF%E5%9B%BE%E6%8B%BC%E6%8E%A5/id1208145167)）。

**难点与风险**
- 状态栏时间/电量变化、导航栏文案不同 → 行签名不匹配；需要"忽略顶部 N% 的 UI 区"策略或先做 L3。
- 纯色/渐变/重复列表（如聊天记录同款气泡）容易歧义 → 需要唯一性检验（匹配区间的行方差/边缘密度）。
- 不同截图来源宽度不一致 → 必须先要求同宽，否则退回普通拼接。
- 输出上限：长截图更容易触发 8192 边缘限制，必须与 N1 长图模式一起上。

**可行性判断**：技术路径清晰、成本集中在匹配准确率与交互兜底，属于"高风险高回报"。**成功标准（spike）**：20 组真实截图（iOS/Android/微信/网页各 5 组）中 ≥90% 自动拼接无需修正，接缝误差 ≤2px，单次合并耗时 <800ms（6 张）。**淘汰条件**：自动成功率 <70%，或需要引入服务端模型。

**工作量**：L（2–4 周，含手动微调 UI）。

### 8.2 M2 · 智能缝隙（内容感知 seam 与样式包）

**用户任务**：用户想让拼出来的长图"看起来是一张图"，而不是几张图叠在一起。现在的波浪缝已经是差异化，但只有开/关。

**为什么是我们**：缝隙是拼接产品独有的视觉对象，通用拼图/设计工具不会做；它能把"拼接"这件事变成有辨识度的品牌资产。

**方向**
1. **样式包**：正弦波（现有）、锯齿、撕纸边、笔刷边、直线 + 渐变遮罩；参数（振幅、相位、颜色、方向）。
2. **内容感知路径**：在两张图交界处计算边缘能量图（下采样到 512 宽），用动态规划找一条"能量最低"的路径（避开人脸/文字/主体），再平滑成 seam。这比固定正弦更"聪明"，且完全本地。
3. **主题化**：缝隙颜色跟随深浅主题；导出时提供"无缝隙/细缝/宽缝"三档。

**与现有管线结合点**
- 现有 `createEdge` + `createImageClipPath`（`stitchLayout.js:88-96`、`stitchRenderer.js:140-253`）已经是"路径 → clip"结构，把正弦函数换成"路径提供者"即可。
- 内容感知路径在 Worker 内对下采样图计算，输出归一化路径点；渲染时按 2px 步长采样（当前是 4px），保证曲线平滑。
- 与 X1 的每图裁剪共用边界定义，避免两套几何。

**难点与风险**
- 缝隙会同时切两张图，clip 联合区域的几何比单图复杂；网格布局横竖缝交叉处需要特殊处理。
- 20MP 输出下路径采样成本；需限制路径分辨率再放大。
- 视觉主观性强，需要真实图像评审，不能只靠单测。

**可行性判断**：纯 Canvas + Worker 可完成，风险中等。**成功标准**：5 种样式在照片/截图/纯色 3 类图像上视觉评审通过；生成耗时 <150ms（6 图）；可一键关闭。**淘汰条件**：内容感知路径在真实图上频繁切到主体（可用人工评审否决）。

**工作量**：L（2–3 周）。

### 8.3 M3 · 自动去状态栏 / 尾部重复

**用户任务**：iOS 截图顶部有状态栏（时间/电量/信号），底部有 Home Indicator；连续截图拼起来会出现重复的顶部/底部条。用户希望自动去掉，而不是手动裁剪。

**为什么是我们**：这是"长截图"场景的最后一公里，与 M1 共享匹配内核；做成了会显著提升"专业感"。

**做法**
1. 收集所有输入图的顶部/底部条带（如顶部 8%、底部 6% 高度），做跨图行签名比对：若多张图在相同位置出现高度相似条带，判定为系统/应用 chrome，自动裁掉。
2. 对尾部：若最后一张图的顶部与上一张尾部重复，直接用 M1 的重叠检测裁掉。
3. 所有自动裁剪都给出"已自动裁剪 N px"提示与一键撤销，避免误裁。

**难点与风险**
- 不同机型/系统版本的状态栏高度不同；App 顶部导航栏属于"内容"还是"chrome"难判定。
- 误裁会切掉用户内容，必须可撤销、默认保守（宁可不裁）。
- 与 M1 的输入约束（同宽、同应用）耦合。

**可行性判断**：中等。**成功标准**：30 组 iOS/Android 截图，正确裁剪率 ≥85%，误裁率 <5%，且全部可撤销。**淘汰条件**：误裁率 >10% 或无法稳定区分导航栏。

**工作量**：M/L（1–2 周，在 M1 的匹配函数之上）。

### 8.4 组合判断

- **M1 是主押注**：它定义"网页端长截图"这个品类，且能复用现有 Canvas 管线。
- **M3 是 M1 的延伸**：共享匹配内核，建议 M1 spike 成功后立刻做 M3。
- **M2 是品牌押注**：不依赖 M1，可独立推进；即使 M1 失败，M2 仍能强化"缝隙"识别度。
- 三者都不引入上传、不引入模型服务，符合红线。

## 9. 如何衡量（不破坏隐私承诺）

### 9.1 原则

- **不引入第三方分析脚本**、不设 cookie、不做设备指纹、不上传图片/文件名/内容。
- 能通过"公开数据/服务器日志/用户主动提供"得到的指标，就不在页面里埋点。
- 涉及用户行为的细粒度数据（导出次数、格式分布、布局偏好）**默认不采集**；如未来确需，只做"用户主动导出/分享"的本地聚合，并明确征得同意。

### 9.2 指标与采集方式

| 要回答的问题 | 指标 | 采集方式 | 频率 | 目标 / 判读 |
|---|---|---|---|---|
| 新用户能否在 30 秒内完成第一次导出？ | 任务成功率、首次导出耗时 | 可用性测试（n=5–8，每期 1 轮，远程/现场） | 每期 1 次 | 成功率 ≥90%，中位耗时 ≤90s |
| 用户是否理解"本地处理"？ | 5 秒测试中能否说出"不上传/本地/长图" | 5 秒测试（n≥8） | 每期 1 次 | ≥80% 说出核心卖点 |
| 生成失败/崩溃多不多？ | 生成失败率、错误类型分布 | **仅本地**记录错误摘要；用户点"反馈"时预填、由用户主动发出 | 持续（本地） | 主动反馈样本中失败率 <1%；无白屏 |
| 性能是否达标？ | LCP、CLS、INP | CrUX 字段数据（Chrome 公开数据集，无需埋点；流量不足时不可得）+ CI Lighthouse 实验室数据 | 月度 / 每次 PR | 实验室 LCP <2.0s、CLS <0.1；主包 gzip 预算内 |
| 是否有人持续使用？ | 回访、来源 | 托管平台的聚合访问日志（无 cookie、保留 ≤30 天、仅路径/日期/粗粒度 UA） | 月度 | 回访占比趋势向上；仅作方向判断，不做用户级分析 |
| 需求是否真实？ | issue/反馈主题分类 | GitHub Issues/Discussions + 应用内反馈链接（预填 UA/构建号，用户主动发送） | 每周归类 | "输出尺寸/格式""长图糊""裁剪/对位"三类占比 |
| 质量是否守住？ | e2e 通过率、axe critical 数、导出格式回归 | CI（X8/X7） | 每次 PR | e2e 100% 通过；axe 0 critical |
| 改版是否变慢/变差？ | 包体积、首屏资源数 | `vite build` 产物 + CI 预算断言 | 每次 PR | 主包 gzip 预算（建议 ≤120KB，按实际基线定） |

### 9.3 明确不做的"度量"

- 不做页面级事件埋点（按钮点击、导出次数、格式分布、布局偏好）。
- 不做用户 ID、会话回放、热图、A/B 分流服务。
- 不把"隐私政策"当成免责声明——**能自证就不靠声明**：在 UI 提供"本地处理"说明，并教用户用 DevTools → Network 验证"导出时没有上传请求"。

## 10. 风险、依赖与协作

| 风险/依赖 | 说明 | 应对 |
|---|---|---|
| **视觉改版并行** | 页面样式由其他成员改动中；本路线图只定义能力与交互要求，不锁定布局/样式 | 新控件由视觉改版负责人统一落位；采用语义化结构（role/label）便于 e2e；N2/N4/X7 需与其对齐 |
| **渲染管线单点** | `StitchCanvas` 现仍负责编排；设置面板/舞台已拆出，但解码/绘制/导出尚未抽 hook，X1/X2 会继续改它 | Sprint B 前把「加载/缓存/绘制/导出」抽成 hook 或函数边界，用 e2e 守行为 |
| **隐私回退风险** | IndexedDB（N4）、诊断导出（第 9 节）都可能被误解为"存了/传了数据" | UI 明示存储位置与清除入口；诊断日志只本地生成，需用户主动发出；上线前做一次"Network 面板无请求"验证 |
| **浏览器兼容** | WebP/OffscreenCanvas 依赖 Safari 版本；Share Target 仅 Chromium；HEIC 仅 Safari | 全部做能力探测与降级；核心导出路径不依赖新 API；兼容矩阵来自 [caniuse](https://caniuse.com/)（附录） |
| **新增依赖膨胀** | PDF、HEIC、i18n 都可能引入包 | 体积预算门禁；PDF/HEIC 按需动态加载；优先手写轻量实现 |
| **长图内存** | 20MP Canvas 在低端机/ Safari 上可能分配失败 | N3 的预算提示 + 长图模式可回退；导出失败给出可操作建议（降尺寸/切片） |
| **6 张上限的竞争压力** | 竞品宣称 20/30/300 张，用户可能质疑 | 用"6 张内的质量与速度"回应；L4 仅作为有条件的实验，不作为卖点承诺 |
| **文案与技术债** | "6 张"硬编码 4 处、UI 全中文 | N2/X6 一并收敛到常量与文案表；改上限只改一处 |
